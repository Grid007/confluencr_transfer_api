# Assumptions

The brief leaves some points open. Each decision below is deliberate, enforced in code, and covered by a test.
Rationale for the larger ones is in [docs/adr/](docs/adr).

## Routing and identifiers

1. Transactions are created with `POST /v1/transactions` and `account_id` in the body, because the brief lists `account_id` as a field of the transaction. Balance and history stay under the account: `/v1/accounts/{id}/balance` and `/v1/accounts/{id}/transactions`.
2. Business routes are versioned (`/v1`). `/health` and `/docs` are not.
3. Ids are UUIDs generated by the server. Clients cannot supply `id`, `created_at` or any other server-owned field.
4. A syntactically invalid id is a `400` validation error. A valid id with no matching row is a `404`.
5. Extra read endpoints (`GET /accounts/{id}`, `GET /transactions/{id}`, `GET /transfers/{id}`) exist so every created resource can be fetched and verified.

## Money

6. Amounts and balances are decimals with exactly two places, stored as `NUMERIC(19,2)` and serialised as JSON strings (`"150.00"`). Floats are never used for money.
7. Input may be a JSON number or a numeric string. The grammar is strict: no exponents, signs, separators or whitespace.
8. A single amount must be between `0.01` and `1,000,000,000,000.00`. The upper bound keeps every accepted JSON number exactly representable.
9. More than two decimal places is rejected with `400`. It is never rounded, because silent rounding would move money the caller did not ask to move.
10. The ledger is single-currency. There is no currency field.
11. A debit may take the balance to exactly `0.00`. One cent more is rejected.

## Request fields

12. Request bodies and query strings are strict. Unknown fields are rejected with `400 UNKNOWN_FIELD`. This is how "the client must not be allowed to set the balance" is made observable, instead of silently dropping the field.
13. `name`: trimmed, 1–100 characters, any printable Unicode, control characters rejected, need not be unique.
14. `description` is optional (the brief's required-field list does not include it). It is trimmed, at most 255 characters, and an empty value is stored as `null`.
15. `reference_id` is a client-supplied idempotency key: 1–128 characters, no leading or trailing whitespace, no control characters, compared exactly (case-sensitive, never trimmed).
16. `type` is case-sensitive: `credit` or `debit` only. `CREDIT` is rejected.
17. A request that is invalid in several ways reports every failing field in one response.

## Semantics

18. A duplicate `reference_id` for the same account returns `409` with the existing transaction in `error.context`. No row is created and the balance is unchanged. The new request's payload is not compared: the first request wins.
19. The duplicate check runs before the balance check, so replaying a debit that has since become unaffordable is a `409`, not a `422`.
20. Insufficient balance is `422 INSUFFICIENT_BALANCE`. `409` is reserved for "already exists" and lock conflicts.
21. Rejected or failed requests are not stored. Only successful transactions exist in the ledger.
22. Every transaction stores `balance_after`, the account balance immediately after it, so history is auditable and the invariant "balance = sum of transactions" can be checked from the data alone.
23. When several checks would fail, they are reported in a fixed order: media type, size, JSON syntax, schema, account existence, duplicates, balance.

## Pagination and ordering

24. Pagination is 1-based. `page` defaults to 1, `limit` to 20 (maximum 100). Invalid values are rejected, never clamped.
25. The response meta uses the brief's wording: `current_page`, `page_size`, `total_records`, `total_pages`. `has_next` and `has_previous` are added for convenience.
26. A page beyond the last returns `200` with an empty `data` array and accurate meta. An account with no transactions has `total_pages: 0`.
27. History is ordered by `created_at` descending, then by an insertion sequence, so rows created in the same millisecond have a stable order.
28. `created_at` is read from the database clock after the account row lock is taken, so a request that waited for a lock is stamped after the transaction it waited for. Both legs of a transfer share one timestamp.
29. Offset pagination can shift if new transactions arrive between two page requests. The brief asks for page/limit, so cursor pagination was not used.

## Immutability

30. Transactions and transfers cannot be changed or deleted through the API: `PUT`, `PATCH`, `DELETE` and any other verb return `405` with an `Allow` header.
31. The same is enforced in the database with triggers, so direct SQL cannot alter or delete a ledger row either. Accounts are also frozen except for `balance`, and cannot be deleted.

## Transfers (bonus)

32. A transfer is one `transfers` row plus two ordinary ledger rows (a debit on the source, a credit on the destination) sharing a `transfer_id`, the transfer's `reference_id` and one timestamp.
33. `reference_id` is optional for a transfer and generated if omitted. It must be unused as a transfer reference on the source account and as a transaction reference on both accounts. Reusing it returns `409` and persists nothing.
34. Transferring to the same account is rejected (`400`, `SAME_ACCOUNT`), and by a `CHECK` constraint.
35. If several accounts named in a transfer do not exist, all of them are reported in one `404`.
36. Transfers appear in each account's history as regular `debit` and `credit` rows, and are included by the `type` filter.

## Operations

37. The API has no authentication or authorisation. It was not requested and is called out as a limitation.
38. Lock waits are bounded (`DB_LOCK_TIMEOUT_MS`). A stuck lock returns `409 CONCURRENCY_CONFLICT` with `Retry-After` instead of hanging. With ordered locking, deadlocks cannot occur.
39. Every response carries `X-Request-Id`. A well-formed client-supplied value is echoed; anything else is replaced.
40. `GET /health` returns `200` when the database answers, `503` (in the standard envelope) otherwise.
41. Request bodies above 100 kb are rejected with `413`; non-JSON write bodies with `415`.
42. Migrations are run explicitly (`pnpm db:migrate`, or the `migrate` service in Compose), never on API start, so several instances cannot race.
43. Accounts cannot be updated, closed or deleted through the API.
44. The assessment brief has no section 6. Nothing is missing.
