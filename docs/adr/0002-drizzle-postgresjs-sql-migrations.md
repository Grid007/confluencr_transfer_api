# 2. Drizzle ORM, postgres.js and SQL migration files

**Status:** accepted

## Context

The ledger's correctness relies on row locks, `numeric` arithmetic, constraints and triggers. The data layer must
expose these directly instead of hiding them.

## Decision

Drizzle ORM 0.45 (stable line) on the `postgres` (postgres.js) driver. The schema is TypeScript, migrations are plain
SQL generated by `drizzle-kit generate`, with hand-written trigger SQL added through `generate --custom`. Migrations
are applied by an explicit command (`src/cli/migrate.ts`), never on API start.

## Consequences

- `.for('no key update')`, `set_config`, window functions and raw SQL are first-class.
- Drizzle wraps driver errors in `DrizzleQueryError`; the SQLSTATE is read from the `cause` chain (`pg-error.ts`).
- `drizzle-kit` does not track functions or triggers, so later `generate` runs never try to drop them.
- The generated index DDL was corrected by hand (`DESC NULLS LAST` removed, see docs/TESTING.md).

## Rejected

- **Prisma:** locking and `numeric` handling need raw-SQL escape hatches; heavier client and engine.
- **Raw `pg` strings:** no schema types, harder to keep migrations and code in step.
- **`drizzle-kit push` / sync-on-start:** no reviewable migration history, unsafe with several instances.
- **Drizzle 1.0 RC:** the docs site shows it, but the stable line is what was verified.
